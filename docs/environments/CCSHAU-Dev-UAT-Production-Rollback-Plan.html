4. Git merge & versioning plan

4.1 Branch strategy

feature/*  →  develop  →  uat  →  main (Production)
                                    ↓
                              tag vMAJOR.MINOR.PATCH
BranchPurposeWho mergesDeploy
feature/*Single change / ticketDeveloper via PR → developOptional preview
developIntegration / DevelopmentTeamDev environment
uatFrozen UAT candidateLead via PR from developUAT environment
mainProduction onlyLead via PR from uatProduction + tag

4.2 Merge rules (secure process)

  • No direct push to uat or main — Pull Requests only
  • Require CI green (lint + test + build) before merge
  • Require at least 1 code review on PRs into uat / main
  • Block force-push on uat and main
  • Keep repository private; least-privilege collaborator roles
  • Never commit secrets; enable GitHub secret scanning / push protection

4.3 Semantic versioning

Version partWhen to bumpExample
MAJORBreaking schema/API/frontend contractv2.0.0
MINORNew feature (CMS module, page type)v1.4.0
PATCHBugfix / security patch / hotfixv1.4.1
Version package: Tag vX.Y.Z = Frontend commit + API (same commit) + list of migration filenames applied for that release (recorded in release notes).

4.4 Hotfix merge path

main → hotfix/xxx → PR into main → tag vX.Y.Z+1 (patch)
                  ↘ merge hotfix back into uat and develop

7. Database plan (Supabase)

7.1 Source of truth

supabase/migrations/*.sql   ← versioned in Git
Apply order: Dev → UAT → Production (same files)

7.2 Rules

  • New change = new migration file (never edit applied migrations)
  • Naming: timestamp + description (existing convention)
  • Record which migrations are part of release vX.Y.Z in release notes
  • Prefer additive/backward-compatible migrations when possible (easier rollback)

7.3 Apply steps (per environment)

# Link the target project, then push migrations
npx supabase link --project-ref <ENV_PROJECT_REF>
npx supabase db push

7.4 Data safety

  • Dev/UAT use test/CMS sandbox content — not Production citizen/university live content copies unless anonymized
  • Production: keep Supabase Pro daily backups enabled (already documented)
  • Before risky Production migration: take a manual backup / note restore point time

8. Secure code practices

Repository & process

  • Private GitHub repo
  • Branch protection on uat / main
  • PR + review + CI required
  • Secret scanning / push protection
  • Least-privilege collaborator access
  • No force-push to protected branches

Code & secrets

  • Never commit .env.local / real keys
  • Only .env.example placeholders in Git
  • Service role key server-only
  • RLS on Supabase tables
  • Validate inputs in Server Actions
  • Disable Dev login prefill on UAT/Prod

9. Promotion pipeline (step-by-step)

sequenceDiagram participant Dev as Developer participant GH as GitHub participant D as Dev Env participant U as UAT Env participant P as Production Dev->>GH: PR feature → develop GH->>D: Deploy FE+API / apply DB migrations Dev->>GH: PR develop → uat GH->>U: Deploy UAT + DB push Note over U: QA sign-off Dev->>GH: PR uat → main + tag vX.Y.Z GH->>P: Deploy Production FE+API Note over P: db push then smoke test
  1. Create feature/… from develop; implement Frontend/API; add migration if needed.
  2. PR → develop; CI must pass; merge; deploy Dev; db push to Dev Supabase.
  3. Smoke test Dev (public pages + admin actions).
  4. PR develop → uat; merge; deploy UAT; db push to UAT.
  5. QA executes checklist; business/university UAT sign-off.
  6. PR uat → main; merge; create tag vX.Y.Z.
  7. Deploy Vercel Production (auto from main).
  8. Apply Production migrations (db push) after confirming release notes / backup point.
  9. Production smoke test; mark release complete.
Order tip: For additive DB changes, deploy FE/API first then migrate. For breaking schema changes, migrate in a compatible two-step release (expand → deploy code → contract), or take a maintenance window with clear rollback.

10. Rollback plan (if issue found)

10.1 Decide what failed

SymptomLikely layerFirst action
UI/admin broken, DB data OKFrontend / APIRedeploy previous Vercel Production deployment
API errors / 500s after deployAPI / env varsCheck logs + redeploy previous tag
Data corruption / failed migrationDatabaseRestore backup or run reverse migration
Everything broken after releaseAllRollback FE/API to previous tag and restore DB to pre-release backup

10.2 Frontend + API rollback (fastest)

  1. Open Vercel → Project → Deployments.
  2. Find last known-good Production deployment (or tag vX.Y.(Z-1)).
  3. Promote/Redeploy that deployment to Production.
  4. Verify /api/health, homepage, admin login, one CMS write.

Git alternative:

git checkout main
git revert <bad-commit>   # or reset only if not shared / with approval
git push
# tag patch: vX.Y.Z+1-rollback

10.3 Database rollback

Preferred: reverse migration

If change is reversible, add a new migration that undoes it (drop column added, restore constraint, etc.). Apply via db push. Keeps history clean.

Emergency: restore backup

Supabase Dashboard → Database → Backups → restore to point before release. Follow docs/ops/backup-restore-guide.md. Expect downtime; coordinate.

Critical: After a DB restore, Frontend/API must run a version compatible with that schema. Always roll FE/API back to the tag that matches the restored DB version.

11. Release checklist

Before UAT

  • □ PR reviewed; CI green
  • □ Migrations listed
  • □ UAT env vars verified
  • □ Dev smoke test passed

Before Production

  • □ UAT signed off
  • □ Production backup / restore point noted
  • □ Release notes include tag + migrations + rollback target
  • □ NEXT_PUBLIC_DEV_PREFILL_LOGIN=false on Prod
  • □ Cron secrets present if cron used

After Production

  • □ Health endpoint OK
  • □ Public homepage + one college page OK
  • □ Admin login + one content update OK
  • □ Upload / Azure URL OK (if touched)
  • □ Tag vX.Y.Z pushed to GitHub

If rollback needed

  • □ Identify layer (FE/API vs DB vs both)
  • □ Redeploy previous Vercel deployment / tag
  • □ Reverse migration or restore DB if required
  • □ Re-test checklist
  • □ Post-incident note: cause + fix version

12. Phased implementation roadmap

PhaseActionsOutcome
Phase 1 Create develop + uat from main; protect main/uat; document release notes template Merge path exists
Phase 2 Create Dev + UAT Supabase projects; copy schema via migrations; wire Vercel env vars per branch Isolated FE/API/DB
Phase 3 Enforce PR-only promotion; map Vercel Dev/UAT/Prod; start tagging Production releases Versioned releases
Phase 4 Practice one rollback drill on UAT (redeploy + reverse migration) Proven rollback
One-line summary: Promote Frontend + API + Database together through develop → uat → main, tag every Production release, keep secrets out of Git, and always retain a previous deploy + DB restore point for rollback.
